### Overall assessment

**Strengths.** Ports-and-adapters with factory-injected dependencies, applied consistently and backed by shared contract suites. The operations domain is a careful compare-and-set, transactional-outbox, idempotent-handler design with one state table. Auth is hardened by design: own JWKS fetch through the CDP proxy with stale-while-revalidate, deny-by-default route `access`, every refusal audited, no identity header trusted. Logging is PII-aware by construction (`fail-action`, redact paths, IDs only). The worker's GitHub client refuses every write but two allow-listed dispatches. Tests are deep as well as many (negative and concurrency paths), and the worker sits at 100 % lines. Comments explain why, not what.

**Top risks.** F1 (one failing operation stalls all GitOps progress), F2 (the two highest-stakes journeys lose idempotency on retry, and the one-time research secret with it), F3 (dependency hygiene past the gate), F4 (a missing GitHub secret gives wrong answers, not a failure). After those, the main maintenance cost is dual representations and inconsistent idioms (F6, F8, F9, F11, F12).

**Must-fix before first external users:** F1, F2, F3, F4. **Should-fix batch:** F5 to F17, F23, F24. **Nits:** F18 to F22.
